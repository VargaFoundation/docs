Open work items from another system (HTTP triggers)

Your error tracker raises an alert on billing-api; you want a work item opened in the ship-a-change workflow, with the alert's details, without anyone copying it by hand. The error tracker cannot speak A2A, but it can POST JSON to a URL. An HTTP trigger turns that JSON into a work item.

What you will be able to do: declare a trigger, map the sender's JSON to a work item's title, description, labels and fields, mint the trigger's token, give the URL to the sender, and know what each answer means.

Before you start:

  • a project whose tracker is Choregos's own (the internal tracker): a trigger does not open issues in an external tracker;
  • the right to change the project's connectors, to mint the token;
  • a workflow to open the work items in (here ship-a-change, whose metadata.inputs require a ticket field).

A trigger has its own token and no person behind it. It answers with the work item's id and reports nothing afterwards: to follow the work, use A2A or the REST API.

1. Declare the trigger​

Open the project, then Settings › Connections, card Triggers. In Triggers (JSON), declare it, then Save:

[
  {
    "name": "error-alert",
    "title": "Fix: {/title}",
    "body": "Seen in {/culprit}. Details: {/url}",
    "key": "/id",
    "labels": ["bug", "{/level}"],
    "fields": { "ticket": "/issue_key", "priority": "/priority" },
    "workflow": "ship-a-change",
    "when": { "/level": ["error", "fatal"] }
  }
]
KeyWhat it does
namethe trigger's name, in its URL: lower-case letters, digits and -
titlethe work item's title; {/pointer} is replaced by the value at that JSON pointer of the payload
bodythe work item's description, with the same placeholders
keya JSON pointer to the sender's own id: while a work item opened with that id is open, another call with it opens nothing
labelslabels, with placeholders; trigger:<name> is always added first
fieldsfield: pointer: the work item's fields, which keep the value's JSON type and are checked by the workflow's metadata.inputs; a missing value is left out
workflowthe workflow to open it in; without it, the project's routing chooses, then its default
whenpointer: value or pointer: [values]: the call opens something only when every condition holds
authtoken (the default) or signature, see Signed calls

A placeholder whose value is missing renders as nothing; a number or an object renders as JSON.

2. Mint its token​

On the trigger's line, choose Mint the token. The token (it starts with chtrg_) is shown once: Shown once: copy it now. The previous token no longer works. Minting again replaces it.

The line also shows the URL to call:

POST https://choregos.example.com/api/v1/webhooks/triggers/acme/billing-api/error-alert

3. Give the URL and the token to the sender​

In the sender's webhook settings, set the URL, the method POST, the header Authorization: Bearer chtrg_... and the content type application/json. A sender that cannot set a header may send X-Choregos-Token: chtrg_... or add ?token=chtrg_... to the URL instead.

Try it from a terminal:

curl -s -X POST "https://choregos.example.com/api/v1/webhooks/triggers/acme/billing-api/error-alert" \
  -H "Authorization: Bearer $TRIGGER_TOKEN" -H 'Content-Type: application/json' -d '{
  "id": "4f1c9e2a",
  "issue_key": "ERR-311",
  "title": "ZeroDivisionError in invoice totals",
  "culprit": "billing/invoices.py in total_with_vat",
  "url": "https://errors.example.com/issues/4f1c9e2a",
  "level": "error",
  "priority": "high"
}'

You can also fire it from the console, with Fire under Fire by hand with a payload: the same mapping applies.

What you should see: HTTP 202, and the work item's id:

{
  "accepted": true,
  "duplicate": false,
  "outcome": "created_work_item",
  "work_item_id": "0b7e6a1c-43f8-7d2a-9c55-1e2f3a4b5c6d",
  "work_item_key": "BIL-13",
  "workflow": "ship-a-change"
}

The work item is titled Fix: ZeroDivisionError in invoice totals, labelled trigger:error-alert, bug and error, with the fields ticket: ERR-311 and priority: high.

What each answer means​

outcomeWhenWhat happened
created_work_itema new calla work item was opened and started
already_opena call whose key names a work item still opennothing new; the answer names that work item
reopeneda call whose key names a work item that has endedthe same work item starts again
ignoredthe payload does not match whennothing was opened

A delivery sent twice (the same Idempotency-Key header, or without one the same body) answers "duplicate": true and starts nothing. Every call, refused ones included, appears in the project's Received events, without the payload's text.

HTTPWhyFix
202accepted, including ignored and duplicatesnothing
401an invalid token, or a missing or wrong signaturemint the token again and update the sender
404no such organisation, project or trigger, or the trigger has no token yetcheck the URL, mint the token
409the project's tracker is externaltriggers open work items in the internal tracker only
413a body larger than 256 KiBsend less
422not a JSON object, no text or number at key, or fields the workflow refuses (the answer lists them)fix the mapping or the payload
429too many calls from one address (600 a minute by default)wait for Retry-After

Signed calls​

With "auth": "signature", the trigger takes no bearer token: each call carries X-Choregos-Signature: sha256=<HMAC-SHA256 of the body>, in hex or base64, computed with the trigger's signing secret (it starts with chsig_), shown once with the token when you mint it. Use it for senders that sign their webhooks, such as many monitoring and ticketing tools.

Other ways work starts​

  • From your tracker: an issue labelled agent-ready starts in Choregos; start rules start other items, for instance a Jira bug of a given type or an issue carrying two labels. They are edited as JSON in the same Triggers card, under Tracker start rules (JSON) (usage reference).
  • On a schedule: a project can open a work item on a cron schedule, for a weekly dependency update or a nightly check (usage reference).
